# Native SRTP and audio replacement evidence

Analyzed 2026-10-21, static arm64 instructions only. Target: installed `ZaloCall`, SHA-256 `f1ac81228f235e92d480dfe4619d568b0a84a5abd70fc73256dcab5f73aa3f3e`. Addresses are preferred Mach-O virtual addresses, not ASLR runtime addresses. Source: `/tmp/zalo-call-analysis/helper-arm64-assembly.txt`; generated by local disassembler in the parent investigation. No native runtime, network, credential access, or original engine reuse performed for this report. REA native decompiler provider was unavailable; findings below are instruction traces, not recovered original source or runtime evidence.

## Confirmed cipher setup

`cricket::SrtpSession::DoSetKey` at `0x100299250` selects precisely:

| Internal profile | RTP | RTCP |
| --- | --- | --- |
| 1 | `srtp_crypto_policy_set_rtp_default` (AES-CM-128 / HMAC-SHA1-80) | same default |
| 2 | `srtp_crypto_policy_set_aes_cm_128_hmac_sha1_32` | default SHA1-80 |
| 3 | `srtp_crypto_policy_set_aes_cm_128_null_auth` | same null-auth |

The actual call sites are `0x1002992b8`, `0x1002992c8`, `0x1002992d0`, `0x1002992e0`, and `0x1002992e8`. Other integers fail this function. Do not infer AES-GCM support from unrelated linked libsrtp symbols: this setup path accepts only profiles 1–3.

`rtc::GetSrtpKeyAndSaltLengths` at `0x10029a280` gives 16 key bytes and 14 salt bytes for each accepted profile; `DoSetKey` at `0x10029930c–0x100299318` requires the provided length to equal their sum, **30 bytes exactly**. It passes the raw pointer into libsrtp policy; there is no KDF or text decoding in this layer. Policy at `0x100299320–0x100299330` sets replay window 1024 and allows repeat transmission. `srtp_create` and `srtp_update` are called at `0x1002993b8` and `0x100299388`.

`zrtc::SrtpTransport::SetRtpParams` at `0x100299d40` creates two independent `cricket::SrtpSession` objects, with `SetSend` at `0x100299df8` and `SetRecv` at `0x100299e14`. Use separate sender and receiver state, even when both use identical key material. RTP protection/unprotection delegates to libsrtp. RTCP uses `srtp_protect_rtcp` and `srtp_unprotect_rtcp` (`0x10029908c`, `0x1002991c4`); don't treat SRTCP as encrypted RTP.

### Follow-up: relay RTCP transform

`SrtpTransport::OnSendPacket` and `OnReadPacket` first classify media bytes with `InferRtpPacketType`. The RTCP branch calls `SrtpSession::ProtectRtcp` / `UnprotectRtcp` (`0x100299938–0x100299990`, `0x100299600–0x100299658`); those wrappers directly call libsrtp `_srtp_protect_rtcp` / `_srtp_unprotect_rtcp` (`0x1002999074–0x1002999098`, `0x10029991ac–0x10029991d0`). The relay outer envelope is applied after protection on send and removed before unprotect on receive. Audio relay type5 is protected only when negotiated `srtcp` is true; see the exact local/remote equality gate in `zrtc-capabilities-contract.md`.

Crypto policy is asymmetric for profile2: `DoSetKey` selects `aes_cm_128_hmac_sha1_32` for RTP, then calls `srtp_crypto_policy_set_rtp_default` for RTCP (`0x10029992c0–0x10029992d4`). Profile1 uses the default policy for both (`0x10029992b0–0x10029992bc`). The SRTCP implementation must therefore use the default 80-bit RTCP tag for both profiles1 and2, independent of profile2's four-byte RTP tag. Mode3 uses AES-CM with null authentication for both, but the current replacement deliberately rejects it.

The standards shape was cross-checked against [RFC 3711 §3.4](https://www.rfc-editor.org/rfc/rfc3711#section-3.4): append the explicit 31-bit index plus E-bit and authentication tag; encrypt only bytes from offset8 onward; authenticate the complete RTCP body plus index word; and maintain replay state separate from SRTP. `src/call/srtcp.ts` implements this shape for profiles1/2, but there is not yet a native-derived wire vector or real relay capture proving key/SSRC/index interoperability. `src/call/rtcp.ts` creates and parses compound SR/RR + SDES/CNAME. The demo adapter now connects matching SRTCP contexts to relay type5: protect before send envelope, unwrap before unprotect/parse; offline tests cover a synthetic round trip only. This does not prove media readiness.

### Native report generation and scheduling

`AudioRtpRtcp::_create` sets the first byte of `RtpRtcp::Configuration` to 1 before calling `CreateRtpRtcp` (`0x100272808–0x100272894`). `ModuleRtpRtcpImpl` stores that byte at `+0xf68`; `RtcpReportInterval` returns `0x9c4` (2500) when it is set, otherwise `0x3e8` (1000) (`0x1003e9854–0x1003e9868`). This is the interval value exposed to WebRTC, not evidence that packets go out at a fixed 2500 ms cadence: `ModuleRtpRtcpImpl::Process` consults `RTCPSender::TimeToSendRTCPReport(false)` and only then invokes `SendRTCP` with the report flag (`0x1003e9458–0x1003e97d4`); WebRTC owns the final scheduling decision.

`RTCPSender::SendRTCP` delegates to `SendCompoundRTCP` (`0x1003d2800–0x1003d2874`). Its report builders construct Sender Reports with sender info and report blocks (`BuildSR`, `0x1003d0a70`) or Receiver Reports with report blocks (`BuildRR`, `0x1003d0ce4`), then `BuildSDES` includes a CNAME item (`0x1003d0ddc`). The exact CNAME value, live report block contents, first-send timing, and any extra Zalo-specific RTCP feedback remain unknown. The independent builder follows the standard compound shape described by [RFC 3550](https://www.rfc-editor.org/rfc/rfc3550.html), but its CNAME and counters must come from actual negotiated/session state.

The raw audio RTCP callback reaches `Peer::onSendAudioRtcp`, which initializes an audio relay packet with RTCP identity and copies the original RTCP body into it (`0x1001b3f08–0x1001b4034`). It then uses the common media send path, where SRTCP protection is applied before the outer relay envelope. Receive reverses that order before dispatch to the RTCP parser. The independent adapter now follows that packet order for type5. Its report method remains gated until call confirmation and takes an explicit CNAME; there is no scheduler, trusted CNAME source, live report state, or peer interoperability evidence yet.

## Confirmed key origin

`ZRtcConfig` JSON parsing reads string `srtpKey` directly into offset `+0x440` (`0x1001f0430–0x1001f0440`), integer `srtpNoSeq` into `+0x458`, and integer `srtpMode` into `+0x45c`. `CallController::parseCallConfig` starts at `0x10015dba0`; its copy of configuration is based at `this+0x1060`.

Defaults in `ZRtcConfig::init`: the 64-bit zero store at `0x1001ee5a0` clears both adjacent integers `srtpNoSeq` and `srtpMode`. `srtpKey` is assigned the empty string at `0x1001ee590–0x1001ee598`. These are local constructor defaults, not an assertion that server-provided call configuration remains zero.

At `0x10015dbe0–0x10015dc10` it validates the profile with `SupportSrtpCrypto`, stores the accepted profile at `this+0x4c0`, and copies configured `srtpKey` to `this+0x4a8`. If the profile is nonzero and the configured key is empty, `0x10015dc2c–0x10015dcac` plus its outlined copy block `0x10015ed84–0x10015ede8` constructs the key as:

```text
sessionId.substr(0, min(sessionId.length, 30))
```

The source field `this+0xf8` is identified by `getSessionId` (`0x10015d068`) and `setSessionId` (`0x10015d090`). The operation is a raw C++ byte substring, not Base64/hex decoding and not a cryptographic hash. Shorter fallback strings still fail the 30-byte check downstream. This does not prove the live session uses fallback rather than a supplied config key; the actual negotiated settings remain unobserved.

For a JavaScript JSON string converted by the same UTF-8 convention, use `Buffer.from(sessionId, "utf8").subarray(0, 30)`, not JavaScript `sessionId.slice(0, 30)`. A nonempty explicit key is copied as-is (no trim or truncation); an invalid explicit key length does not trigger fallback. JSON-to-string encoding at the application boundary must still be preserved; non-ASCII session identifiers were not observed here.

`Peer::createAndInitSRTP` at `0x1001a1d14` duplicates its supplied key string and constructs two transports. Both `SetUpKey` calls (`0x1001a1e28`, `0x1001a1e40`) receive these same two copies. `Peer::_handleStartCall` fetches the key and mode from its controller at `0x1001a77f0` and `0x1001a77f8`, then invokes the virtual transport constructor at `0x1001a781c`. No DTLS handshake or exporter occurs in the traced explicit-key setup path. This is not a claim that the entire shipped binary lacks DTLS.

## Important nonstandard RTP compatibility behavior

`SrtpTransport` constructor `0x1002994e8` stores `srtpNoSeq` at offset `+0x2c` and a separate boolean at `+0x30`. `SetUpKey` (`0x100299e74`) replaces the selected profile with **profile 3** when `+0x2c` is nonzero (`0x100299ef4–0x100299f00`). It then invokes `SetRtpParams` with that profile for both directions.

`cricket::SrtpSession::ProtectRtp` at `0x100298eb8` saves the RTP sequence number when its noSeq argument is nonzero, writes zero into that field (`0x100298f1c`), calls `srtp_protect` (`0x100298f54`), and restores the original sequence number (`0x100298f70`). Its separate boolean similarly zeroes and restores SSRC (`0x100298f44`, `0x100298f84`). `UnprotectRtp` at `0x1002990a0` mirrors these mutations around `srtp_unprotect` (`0x10029913c`).

Consequences: a standard SRTP library alone is insufficient for this option; an adapter must reproduce the exact header mutation and repeat/replay behavior. Do not change profile1 to null-auth speculatively: the choice is driven by negotiated settings. The traced normal peer path passes boolean false, so SSRC zeroing is not enabled there. Audio and video noSeq are passed separately by constructor arguments; do not assume one generic global value.

Receive replay check is modified in this shipped library: `_srtp_unprotect_mki` calls `srtp_rdbx_check` at `0x1002a1774` and immediately sets its status register to zero at `0x1002a1778`, then continues. Its replay-check return is discarded on this branch. Send-side `srtp_rdbx_check` calls at `0x1002a0934` and `0x1002a0a28` retain conditional handling, with stream `allow_repeat_tx` checked. This explains how repeated cryptographic sequence zero can be accepted on RX without assuming stock libsrtp behavior. This does not establish that every replay/rollover check in every path is disabled; separate index-distance branches are still present. A replacement must test this compatibility explicitly and must not claim an unmodified libsrtp session already interoperates.

## Confirmed Opus and payload properties

`CallController::setCurrentAudioCodec` at `0x10015d424` maps `pcmu` to payload 0 and `pcma` to 8. All other input names are normalized to `opus`; payload becomes **112 when sample rate = 16000, otherwise 113** (`0x10015d4d8–0x10015d508`). The resulting codec descriptor is formatted `%s/%d/%d`. This mapping cannot be copied from browser payload111 assumptions.

`AudioRtpRtcp` construction contains two explicit `AudioDecoderOpus::MakeAudioDecoder` calls: configuration 16000 Hz / 1 channel (`0x100272430–0x100272440`), and 48000 Hz / 2 channels (`0x10027247c–0x10027248c`). `AudioEncoderOpusImpl::SampleRateHz` and `RtpTimestampRateHz` (`0x10036d458`, `0x10036d468`) both return its configured rate field `+0xc`. Consequently, do not assume the 16 kHz native Opus variant uses the ordinary browser 48 kHz RTP timestamp rate without tracing actual selected encoder configuration.

`WebRtcOpus_EncoderCreate` at `0x10036fad0` invokes the linked standard `opus_encoder_create` at `0x10036fb40`; application input0 maps to OPUS_APPLICATION_VOIP (2048), input1 to OPUS_APPLICATION_AUDIO (2049). This establishes library use, not the live negotiated frame duration, bitrate, FEC, DTX, channel mode, or codec rate.

## Replacement decision and remaining gaps

A new implementation can use an independently supplied libsrtp/Opus implementation, rather than load ZaloCall or copy its native code. Prefer terminating browser WebRTC on a separate server media leg, then decode/resample/encode or rewrite RTP for the Zalo leg based on negotiated codec. Direct browser `RTCPeerConnection` cannot be assumed to express the explicit raw SRTP key and nonstandard sequence mutation behavior above.

Still unresolved by this bounded static pass:

- Which incoming/answer configuration sets the active profile/key/noSeq; no live media session was captured.
- Exact proprietary outer relay packet framing, authentication, registration, keepalive, and endpoint selection (other investigation scope).
- Live codec negotiation and timestamp rate, packet duration, RTP extensions and SSRC assignment.
- Whether SRTP/SRTCP is applied on a particular relay/P2P path under `srtpRTCP` and P2P flags.
- Wire-compatible test vectors for header-zeroing options and libsrtp repeat/replay handling.
- Browser microphone to a real remote Zalo participant and return speech: not tested by this report.

Before declaring the engine removed successfully, require an owned-account incoming call with no ZaloCall process, browser accept/hangup, remote-confirmed transmitted speech, decrypted incoming speech, and clean second-call state. Cipher/payload primitives alone do not satisfy that gate.

## Independent standards primitive added

`src/call/srtpRtp.ts` now implements RTP-only AES128 counter mode and HMAC-SHA1 for authenticated profiles1/2 using Node `crypto`; no Zalo binary, external package or network is used. Its KDR is fixed to zero and MKI is absent. Separate send/receive contexts require an explicit SSRC, initial ROC, and initial sequence number. Receive replay protection remains enabled, unlike the observed patched native branch; profile3 and noSeq intentionally fail closed. Contexts must not be reset/recreated to reuse sender key+SSRC+packet index. A low-level AES-CM helper is exported for the standard cipher-vector test and explicitly does not perform authentication/state tracking.

Standards source checked directly: [RFC3711 sections4.1.1/4.3 and appendicesA/B](https://www.rfc-editor.org/rfc/rfc3711). `test/srtpRtp.ts` checks published KDF and first/final AES-CM blocks, explicit nonzero IV field placement, both authentication lengths, tamper rejection without state poisoning, rollover with delayed previous-ROC packets, duplicate/stale replay, and fail-closed lifecycle/unsupported modes. These are offline RFC primitive tests, not an independent code audit or live Zalo interoperability proof. SRTCP, noSeq compatibility, rekeying, and real media transport remain separate unfinished requirements.
